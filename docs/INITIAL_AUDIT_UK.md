# Початковий аудит — 06.11.2026

Стек: Flask/Jinja, vanilla JS/CSS, MySQL/InnoDB, aiogram. Дані номерів,
послуг, меню, клієнтів і заявок редагуються через адмінпанель. Міграції SQL
зберігаються в database/migrations. Автоматизованих тестів не було.

Підтверджені проблеми перед виправленнями:
- Критично: календар house.html використовує демонстраційний масив, звертається
  до rooms.reserved_date, не оновлює URL бронювання, містить фіксовані дати.
- Критично: форма довіряє Telegram ID з прихованих полів без перевірки підпису.
- Немає перевірки минулих дат публічного бронювання номерів; room_has_overlap
  передає межі діапазону в неправильному порядку.
- Повернення з preview втрачає телефон і коментар; дати у формі незмінні.
- Telegram: prices і services відкривають один список; послуга не передається
  в URL бронювання. Умови можуть містити текстові null/none.
- Етапи послуг не мають переходів; кілька етапів одночасно active.
- Вибір послуг має ризик гонки відповідей API; дати недоступні з клавіатури.
- Площа виводиться без одиниць. Заголовки хаотично змішують мови.
- Контакти реалізовані клікабельними div; адреса не має структурного переносу.
- Flash-повідомлення не відображаються в публічному base.html.
- Production: dev-сервер запускається з debug=True, типовий SECRET_KEY,
  немає загального CSRF-захисту адміністративних форм, open redirect login.

Басейн уже є в SQL каталозі services й використовує спільний механізм слотів.
Поле conditions уже редагується в адмінпанелі. Фактичні ціни/умови/наявність
у робочій БД не підтверджені: підключення з доступною конфігурацією відхилено.
Не змінювати ціни, контакти, дані та не запускати seed/migration на робочій БД.
