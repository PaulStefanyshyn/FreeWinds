# Фінальний звіт аудиту «Вільні вітри» — 06.11.2026

## 1. Виявлені проблеми

Критичними були непрацюючий календар номера і втрата дат перед бронюванням,
довіра до Telegram ID з непідписаних полів, неправильний порядок меж у
room_has_overlap, можливість вибору минулих дат/часу та перевірка послуг
тільки за однаковим часом початку без урахування duration_minutes.

Проблеми UX: дубль меню «Ціни» у боті, відсутність прямого вибору послуги,
кілька активних етапів бронювання, відсутність переходів між етапами,
втрата контактів при редагуванні заявки, площа без м², порожні блоки номера,
змішані українські й англійські підписи, неклавіатурні контакти та дати,
недостатня видимість маркерів меню, відсутність публічних flash-повідомлень.

Карта контактів містила маркер іншої назви закладу («Albertville»).
Наявні телефон, адреса й Instagram потребують підтвердження власником.

Технічні проблеми: debug=True при прямому запуску, стандартний секрет сесій,
відсутність CSRF у формах, відкритий зовнішній redirect після входу,
неправильний JSON заявки міг давати серверну помилку. Збій повідомлення
після збереження міг повідомляти клієнту про невдале бронювання.

### Backend та захист

- Публічні дані номера завантажуються тільки за ID з каталогу. Демонстраційний
  DEFAULT_HOUSE_DATA та старий POST, що приймав довільний опис номера, прибрано;
  жодного виклику цього POST у поточному frontend не було. /house без ID веде до номерів.
- Виправлено межі перетину бронювань номерів; минулі дати відхиляються
  при пошуку, перегляді заявки та збереженні публічного бронювання.
- Послуги враховують duration_minutes: перетин часових інтервалів, включно
  із сусідніми днями, та блокування рядка послуги перед створенням.
  Адміністративне відновлення активного статусу перевіряє той самий перетин.
- Телефон та ім’я перевіряються; звичайний браузер має поле імені.
  Telegram ID приймається тільки з перевіреного initData; непідписані hidden-поля
  прибрано. Прострочені/майбутні auth_date та некоректна структура user відхиляються.
- Додано CSRF до всіх POST-форм, включно з адмінпанеллю. GET-форми токенів
  у URL не передають. JSON API користується Telegram-авторизацією, без cookie-login.
- Збережено захист від послідовного повторного підтвердження заявки;
  конкурентне бронювання додатково перевіряється під транзакційним блокуванням.
- Помилка обліку/надсилання повідомлення після збереження не скасовує успіх.
  Це не черга гарантованої доставки: після збою слід перевірити повідомлення в адмінпанелі.
- Debug вимкнено; локальний сервер прив’язано до loopback. Для APP_ENV=production
  заборонені типові SECRET_KEY та ввімкнений Secure-cookie; HttpOnly/SameSite=Lax
  задані явно. Зовнішній next у login відхиляється.
- Оброблено недоступність БД, невалідні JSON та відсутню дату заявки.

Змін схеми БД і міграцій немає. Робочі дані, ціни, телефон, адреса та Instagram
не змінені. Seed SQL не запускався. Папку «правки» не змінено.

### Узгоджена дизайн-система

Джерело токенів — static/css/base.css. Збережено основний синій #315f77,
теплий фон #f5f1e9 та поверхні #fffdf8/#ede7da. Допоміжний текст #655f56,
акцент #91652f. Типографіка Inter/system, адаптивні заголовки, спільні кнопки
.btn-primary/.btn-secondary, border/radius/shadow та page-gutter.

Публічні назви українські, Instagram/Telegram — власні назви. Окремої
англійської локалі в проєкті немає; новий перемикач мов без перекладів не створювався.
Поля мають окремий placeholder звичайної товщини, видимий focus, масштабування
браузера дозволено. Закрите мобільне меню inert; Escape повертає focus кнопці,
Tab утримується всередині відкритого меню. Обов’язкові майбутні етапи disabled.

## 3. Результати тестування

Автоматизовані тести: tests/test_booking.py, стандартний unittest.
**Фінальний результат: 34 тести пройшли, 0 помилок (5,970 с).**
Python compileall і git diff --check також успішні.

Перевірки охоплюють маршрути й локальні ресурси, компіляцію всіх Jinja-шаблонів,
ID/дати номера, відсутні/неправильні/минулі дати, телефон, повернення з preview,
повторне підтвердження, конфлікт на фінальному кроці, CSRF, Telegram-підпис,
авторизацію API, нормалізацію умов/площі, SQL-порядок блокування/перевірки/INSERT/commit,
конфлікт послуг за тривалістю, адміністративне відновлення статусу й callback-и бота.

Браузер: справжні шаблони та JS, окремий tests/ui_server.py з ізольованими
fixtures. Каталог послуг відтворює наявні SQL-записи, номер — тестова fixture.
Це не заміна робочих даних. UI-сервер забороняє MySQL-з’єднання й відправлення
повідомлень; фінальна кнопка не може створити запис у реальній БД.

Перевірено:
- Номер без дат → вибір заїзду/виїзду → форма саме цього номера → preview;
  після повернення збережені ім’я, телефон, коментар і дати.
- Прямий вибір басейну; вибір чанів, бані, більярду, дати й часу;
  стан етапів і повідомлення про необхідність Telegram при підтвердженні.
- Відкриття/закриття мобільного меню, Escape і повернення фокусу.
- Геометрія головної, номерів, деталей номера, послуг, контактів, меню,
  «Моїх бронювань», форми та preview на ширинах 1920, 1440, 1366,
  1024, 768, 430, 390, 360 px. Для перевірених fixtures виходів вмісту
  за межі viewport не виявлено. Візуальні screenshots оглянуті на мобільній
  ширині та після перемикання desktop; окремого реального планшета/iOS не було.
- У захоплених console logs перевірених сторінок немає JS error/warn.
  Відповідь 401 без Telegram — очікувана. Додано favicon із наявного логотипа.
- git diff --check та Python compileall.

Не перевірено і не заявляється успішним:
- Реальний INSERT/rollback/конкурентні транзакції та синтаксис змінених SQL
  на живому MySQL: доступна конфігурація відхиляється, окремої тестової БД немає.
  Користувач погодив ізольоване тестування. SQL-тести використовують mock-cursor.
- Повний сценарій створення бронювання послуги у Telegram WebApp,
  реальна доставка фото/повідомлень, прив’язка й callback через Telegram API.
- Реальні фотографії/довгі описи з робочої БД, заповнений ресторанний каталог,
  всі адміністративні CRUD на живій БД, навантаження й production reverse proxy.
- Окрема сауна: у SQL seed є басейн, чани, баня, більярд; наявність сауни
  у робочій БД невідома. Нової послуги з вигаданою ціною не додано.
- Окремої сторінки «Про заклад» і футера в цьому checkout немає.
- Точна точка карти: адресний пошук не гарантує однозначної геолокації.

## 4. Питання до власника

1. Підтвердити телефон, Instagram, повну адресу з населеним пунктом та офіційне
   посилання/координати карти. Наявний номер схожий на приклад; його не замінено.
2. Для басейну підтвердити, що поточна модель «одна заявка блокує послугу на
   інтервал» відповідає роботі закладу, чи потрібен облік місткості/кількості гостей.
3. Надати умови басейну та інших послуг для поля conditions; підтвердити години,
   сезонність, допустиму тривалість, наявні фіксовані початки слотів 10/12/14/16/18/20.
4. Чи сауна окрема послуга від бані? Якщо так — надати реальні дані й ціну.
5. Який маршрут/контент мається на увазі під «Про заклад»?
6. Для фінальної перевірки потрібна окрема тестова MySQL з копією схеми/знеособленими
   даними та тестовий Telegram-бот/чат. Секрети налаштовувати локально, не в чаті.

## 5. Готовність до Production

**Не готово до деплою без додаткової інтеграційної перевірки й підтвердження даних.**
Виправлення реалізовано й ізольовано перевірено, але відсутність доступної
тестової MySQL не дозволяє чесно підтвердити кінцеве збереження/конкурентність.

Перед релізом потрібно:
1. Перевірити поточну схему/міграції 001–007 на окремій MySQL; не запускати
   schema.sql або seed поверх робочих даних без окремого аналізу й backup.
2. Пройти кімнату й кожну активну послугу до збереження та перечитування запису;
   перевірити два паралельні запити, суміжні дати, перехід через північ,
   адміністративну зміну статусів та зміну duration_minutes існуючої послуги.
3. Підтвердити бізнес-правила й контакти з пункту 4. Зміна тривалості зараз
   застосовується й до перевірки раніше створених записів цієї послуги;
   окремої історичної тривалості у моделі немає.
4. Встановити APP_ENV=production, випадковий довгий SECRET_KEY, правильні
   SITE_BASE_URL/WEB_APP_URL та Telegram-конфігурацію. .env.example — приклад;
   config.py читає змінні процесу, самостійно .env не завантажує.
5. Налаштувати WSGI-сервер, HTTPS/reverse proxy, обмеження запитів до login,
   резервне копіювання, журналювання та перезапуск процесів сайту й бота.
   python app.py та flask run — тільки для локальної перевірки.
6. Узгодити часову зону процесу й MySQL з Europe/Kyiv: перевірки часу зараз
   використовують локальний час процесу. Перевірити сесії/CSRF у реальних
   Telegram Desktop/Android/iOS та звичайному браузері через production HTTPS.
